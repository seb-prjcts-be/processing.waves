About

processing.waves is a Java port of p5.waves v3.3.0 for Processing 4. Same 34 waves, same API shape, same numerical output, just in Java instead of JavaScript.

Why a Java port?

p5.waves lives in p5.js. Plenty of creative coders work in Processing (the Java IDE) for one of these reasons:

  • They want the speed of compiled code for tight rendering loops or pixel-by-pixel field work.

  • They use Processing for offline / high-resolution renders where browser JS isn't the right tool.

  • They teach Processing as a first language and want their students to have access to the same wave vocabulary as the p5.js side.

  • They like Processing 4's tooling: sketchbook, Contribution Manager, the export-to-app pipeline.

The Java port hands those users the same building blocks, with no syntactic translation work each time they pick up a wave-based idea.

Building the library

The challenge of porting wasn't the math: sine, cosine, log, tan, modulo all exist in Java. The challenge was making the output numerically identical to JS for a deterministic seed. Three things matter:

  • FNV-1a 32-bit hash. JS treats the seed as an unsigned uint32 stored in a Number (double). Java's int is signed. seedFrom() returns an unsigned long (the uint32 promoted), so all downstream float math matches bit-for-bit.

  • Mulberry32 PRNG. Identical state transitions to the JS port. Same seed = same sequence on both sides.

  • double-precision math. Internal computations run in double (matching JS Number); the public API returns float (Processing convention). Visually identical, sub-pixel match where deterministic.

Validation

The repo ships a numerical validator in /tests. It runs the JS reference (p5.waves.js) via Node, captures 35 input/output pairs across all 34 waves, then runs the Java port over the same inputs and asserts equality within tolerance.

MetricValue
Cases35 (covers all 34 waves + 1 shift case)
Stable-mode tolerance1e-3
Wild-mode tolerance0.5
Current status35 / 35 pass

Wild mode's looser tolerance is intentional: noise modulation amplifies tiny float-vs-double differences. The wave envelope still matches; only the per-sample chaos detail diverges within the noise budget.

What's the same as p5.waves

  • All 34 wave shapes, names, and indices match.

  • The "gentle / harsh / closing" group taxonomy.

  • Shift, morph, wild, range mapping: same semantics, same numerical output.

  • createSampler() works the same way, including the shift entropy that randomises per session.

What's different from p5.waves

  • Fluent builder instead of object literal. Java doesn't have JS-style options objects. WaveOpts uses chained setters: new WaveOpts().wave("triangle").amplitude(80).

  • No runtime string evaluator. JS p5.waves uses new Function(algoString) internally. Java replaces this with hand-written lambdas, one per wave. The string-eval feature was never exposed via the public API, so there's no surface-level difference.

  • No browser-only conveniences. No DOM, no canvas wrappers. The library is pure math. It plugs into Processing's draw loop just like any other math utility.
